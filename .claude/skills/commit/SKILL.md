# commit — 差分をコミット粒度で提案し、承認後にコミットする

ユーザーが「コミットして」などとコミットを依頼したときに起動するスキル。
差分をそのまま1コミットにまとめたり、確認なしにコミットを実行したりしない。
必ず粒度の提案 → ユーザー承認 → 実行、の順で進める。

## Step 1 — 現状を把握する

以下を並列で実行して現状を把握する。

- `git status`(untrackedファイルも含めて確認する。ただし `-uall` は使わない)
- `git diff`(unstaged)と `git diff --staged`(staged)の内容
- `git log --oneline -10`(直近のコミットメッセージの言語・スタイル・粒度感を把握するため)

## Step 2 — 差分をコミット単位に分割する

diff全体を読み、変更を意味のある単位にグルーピングする。方針:

- 1コミット = 1目的。機能追加・バグ修正・リファクタ・フォーマット調整・依存関係更新などは別コミットに分ける
- 同じ目的に関わる複数ファイルの変更はまとめて1コミットにしてよい
- 目的が異なる変更を1つのコミットに混ぜない
- 差分が小さく分割する意味がない場合は、1コミットのみの提案でよい(無理に分割しない)
- コミットメッセージの言語・スタイル(prefixの有無など)は直近のコミット履歴に合わせる
- コミットの順序は、依存関係(例: 設定変更 → それを使う実装)を考慮して決める

## Step 3 — 提案をテーブル形式で提示する

必ず以下の形式でユーザーに提示する。**この時点ではまだコミットを実行しない。**

| 番号 | コミットコメント | 具体的なファイル |
| --- | --- | --- |
| #1 | {コメント} | {ファイル名} |
| #2 | {コメント} | {ファイル名} |

- ファイルが複数ある場合はセル内に列挙する(`,` 区切りや改行)
- テーブルの後に「この粒度でコミットしてよいか」を一言確認する

## Step 4 — 承認を待つ

ユーザーの明示的な承認(「OK」「いいよ」「それで」など)があるまでコミットを実行しない。
ユーザーが粒度の変更(統合・分割・コメント修正・対象ファイルの除外など)を求めた場合は、
Step 3 のテーブルを更新して再提示し、再度承認を待つ。

## Step 5 — 承認後にコミットを実行する

承認された内容に従い、提案した順番通りに1コミットずつ実行する。

1. 対象ファイルだけを明示的に `git add <file1> <file2> ...` でステージする
   (`git add -A` / `git add .` のような一括ステージは使わない)
2. ヒアドキュメントでコミットメッセージを作成してコミットする:
   ```
   git commit -m "$(cat <<'EOF'
   {承認されたコミットコメント}
   EOF
   )"
   ```
   セッション側から追加のアトリビューション行(Co-Authored-By 等)の指示がある場合は、
   その指示に従ってメッセージ末尾に付与する。
3. 1コミットごとに `git status` で意図しないファイルが混入していないか確認してから次に進む
4. 全コミット完了後、`git log --oneline -N`(Nはコミット数)などで結果を簡潔に報告する

## 注意事項

- pre-commit hookで失敗しても `--no-verify` では回避せず、原因を修正してから再コミットする
- `--amend` は使わない(ユーザーから明示的に依頼された場合を除く)
- `.env` など機密情報を含みそうなファイルが対象に入っていないか、addする前に確認する
- リモートへの `push` はこのスキールの範囲外。ユーザーから別途依頼されない限り行わない
- コミット粒度の提案に関係のない指摘(コードレビューやリファクタ提案など)はこのスキール内で行わない
